## Key Code

### Durable transcript boundaries

The session has no revision or event-sequence field:

```rust
pub struct Session {
    pub id: SessionId,
    pub created_ms: i64,
    pub updated_ms: i64,
    pub model: String,
    pub provider: String,
    pub messages: Vec<Message>,
    // workspace/client metadata...
}
```

`crates/ocean-agent/src/session/mod.rs:5-35`

Current durable boundaries are:

1. **Accepted user input**, before any provider call or tool:
   `crates/ocean-agent/src/lib.rs:1548-1560`.
2. **Every provider-valid completed round**, consuming `TurnCheckpoint` deltas:
   `crates/ocean-agent/src/lib.rs:1758-1770`.
3. **Final run transcript save**:
   `crates/ocean-agent/src/lib.rs:1795-1810`.

The underlying save writes a temporary sibling, `sync_all`, then renames:

`crates/ocean-agent/src/session/mod.rs:359-387`.

These are the exact opportunities to advance a transcript projection revision. Updating only the final save would lose long-running tool-chain granularity; updating only `TurnCheckpoint` would omit accepted user input.

### Runtime event ordering

The normal sequence is:

1. `UserMessage`
2. `AgentStart`
3. Per provider round: `TurnStart`
4. Zero or more `TextDelta` / `ThinkingDelta`
5. `AssistantMessage`
6. If no executable tool batch: `TurnEnd`, then `TurnCheckpoint`
7. If tools:
   - permissions checked sequentially;
   - `PermissionDenied` for denied calls;
   - all `ToolExecutionStart` events for a shared segment, in call order;
   - `ToolExecutionEnd` in actual completion order;
   - side effects immediately after the corresponding end:
     `Render`, `Unmount`, `BrowserActivity`, `SurfacePatch`, or `SlackCanvas`;
   - transcript tool results assembled later in original call order;
   - `TurnEnd`, then `TurnCheckpoint`.
8. Optional max-turn fallback `TextDelta`, followed by checkpoint.
9. `AgentEnd`.

Relevant emission sites:

- Initial/lifecycle: `agent_loop.rs:415-488`
- Streaming/final assistant: `agent_loop.rs:660-800`
- Tool start/completion/cancellation: `agent_loop.rs:940-1110`
- Side effects: `agent_loop.rs:1283-1371`
- Checkpoint construction: `agent_loop.rs:1683-1708`

`TurnCheckpoint` contains only newly durable transcript rows and advances its cursor even without a receiver.

### Agent-to-daemon bridge

`crates/ocean-daemon/src/main.rs:5908-6200` receives runtime events over an unbounded MPSC channel.

Relayed mappings:

- `TextDelta` → `AssistantTextDelta`
- `ModelRerouted` → `ModelRerouted`
- `ThinkingDelta` → `ThinkingDelta`
- `ToolExecutionStart` → `ToolCallStarted`
- `ToolExecutionEnd` → `ToolCallFinished`
- `PermissionDenied` → synthetic paired `ToolCallStarted` + `ToolCallFinished`
- `Render` → `ComponentRender`
- `Unmount` → `ComponentUnmount`
- `BrowserActivity` → `BrowserActivity`
- `SurfacePatch` → stamped `SurfacePatch`
- `SlackCanvas` → `SlackCanvas`

Intentionally not relayed:

- `AgentStart`, `AgentEnd`
- runtime `TurnStart`, `TurnEnd`
- `TurnCheckpoint`
- `AssistantMessage`, `UserMessage`

Daemon lifecycle producers compensate with richer `SessionCreated`, `TurnStarted`, and `TurnFinished` events (`main.rs:5765-5794`, `6245-6388`).

Important seam: bridge events call `bridge_bus.emit(...)` directly, while lifecycle events use `emit_agent(...)`. A journal attached only to `emit_agent` would miss deltas, tools, components, browser activity, and patches.

### Current SSE bus and replay

`AgentEventBus` is:

- process-memory only;
- global, then filtered per subscriber;
- bounded by count and serialized bytes;
- assigned random UUID envelope IDs;
- recorded into replay history before broadcast;
- atomically subscribed and snapshotted under the same mutex.

`crates/ocean-daemon/src/bus.rs:151-332`

SSE supports:

- `?session_id=<id>`: only matching session;
- `?all=1`: explicit global firehose;
- `Last-Event-ID`: events after a retained UUID;
- `?session_id=<id>&replay=1`: entire *currently buffered* history for that session.

`crates/ocean-daemon/src/main.rs:6653-6884`

This is not exact snapshot+tail across restart or replay-buffer eviction. Unknown/aged-out `Last-Event-ID` returns no replay, and lag produces an error rather than authoritative recovery.

### Permissions rail

Permissions are separate from `AgentEventBus`:

- `DaemonPermissionPolicy` owns mode, request/session IDs, legacy `EventBus`, registry, cancellation, per-turn dedupe, and secret decision token:
  `main.rs:542-565`.
- Decisions require the matching per-turn token before removing the waiter:
  `main.rs:1778-1859`.
- Decisions are delivered to the runtime and emitted as legacy `OceanEvent::PermissionDecision`:
  `main.rs:1861-1909`.
- Runtime denial becomes a synthetic tool start/finish on the agent rail:
  `main.rs:6012-6042`.

Therefore exact projection of operator-visible permission state must capture permission requested, resolved, cancelled, and denied states from the permission/request rail—not merely `AgentEvent::PermissionDenied`.

### Components and browser events

## Architecture

```text
HTTP turn intake
  -> daemon emits SessionCreated / TurnStarted
  -> AgentRuntime::prompt
      -> accepted user session::save
      -> runtime AgentEvent channel
          -> ocean-agent forwards event to daemon
          -> TurnCheckpoint also updates session JSON immediately
      -> final session::save
  -> daemon bridge converts live runtime events to AgentTurnEvent
  -> global AgentEventBus
      -> bounded in-memory replay
      -> session-filtered SSE tail
  -> daemon emits TurnFinished
```

### Minimal producer coverage for exact snapshot+tail

A minimally complete journal cannot instrument only one existing bus helper. It must cover:

1. **Transcript revision producers**
   - accepted-user save;
   - every `TurnCheckpoint` save;
   - final save/reconciliation.
2. **Daemon lifecycle**
   - `SessionCreated`;
   - `TurnStarted`;
   - `TurnFinished`, including failure/cancellation telemetry.
3. **Live assistant content**
   - text and thinking deltas;
   - model reroutes.
4. **Tool lifecycle**
   - start and finish;
   - preserve runtime tool-call identity rather than only daemon-random IDs;
   - completion order as emitted.
5. **Permission lifecycle**
   - request/pending;
   - allow, allow-session, deny;
   - cancellation/expiry and request state changes.
6. **Component/browser/surface state**
   - render, unmount;
   - browser activity;
   - surface patches;
   - Slack canvas events/fulfillments if displayed in session detail.
7. **Stable ordering**
   - one monotonic per-session sequence/revision allocated at the shared producer boundary;
   - snapshot returns an `as_of_revision`;
   - tail subscribes strictly after that revision.
8. **Atomic seam**
   - snapshot/revision read and live subscription must share synchronization or use durable query-after-revision semantics.
   - The current UUID/bounded replay seam is insufficient.

`ToolCallChunk` exists in the SDK but no runtime producer was found; it need not be invented for minimal coverage, but the journal schema should remain forward-compatible.

## Constraints and Residual Risks

- Session JSON remains capped history; a journal must define retention independently or “exact” eventually becomes false.
- Advancing journal revision separately from session-file rename risks split-brain. A transaction/outbox or explicit recoverable commit protocol is needed.
- Randomly regenerated turn IDs in `turns_from_detail` prevent stable identity across snapshots.
- Runtime tool IDs are replaced with daemon UUIDs; exact correlation across snapshot/restart requires persisting a stable mapping or retaining runtime IDs.
- Current SSE replay is memory-only and silently gives no history for aged-out/unknown anchors.
- Permission and request events live on the legacy rail, while agent output lives on the agent rail.
- Surface patch revision authority belongs to the client ledger; the daemon must not fabricate an authoritative canvas revision.
