## Key Code

### Authoritative read APIs

- `GET /v1/agent/sessions` and `GET /v1/agent/sessions/{id}` are the product session APIs; `GET /v1/agent/events` is the product turn SSE rail (`crates/ocean-daemon/src/main.rs:648-664`).
- `GET /v1/requests` and `GET /v1/permissions` are global daemon snapshots; `/v1/events` is the legacy global SSE rail (`crates/ocean-daemon/src/main.rs:681-688`).
- The agent session list is bounded/paginated and each summary contains `active_turn`, derived from the global live request registry (`crates/ocean-daemon/src/main.rs:8796-8862`; DTO at `crates/ocean-agent-sdk/src/lib.rs:444-476`).
- Session detail returns `AgentSession` plus reverse-chronological `AgentTurn`s. A turn has `status` and optional `error` (`crates/ocean-agent-sdk/src/lib.rs:173-193,480-490`; handler `crates/ocean-daemon/src/main.rs:8933-9031`).

### Running/error/permission vocabulary

```rust
pub enum RequestState {
    Queued, Running, WaitingForPermission, Cancelling,
    Cancelled, Completed, Errored,
}
```
`crates/ocean-core/src/lib.rs:51-60`

`RequestStatus` carries `request_id`, optional `session_id`, state, optional `permission_id`, optional message, and timestamps; `GET /v1/requests` returns all registry entries sorted newest-first (`crates/ocean-core/src/lib.rs:660-692`; `crates/ocean-daemon/src/main.rs:6351-6368`). This is already a cross-session running/error/waiting snapshot.

`PermissionStatus` carries permission/request/session IDs, tool, reason, args, and creation time. `GET /v1/permissions` returns every currently pending waiter, newest-first (`crates/ocean-core/src/lib.rs:696-718`; `crates/ocean-daemon/src/main.rs:6343-6374`). It does not expose the decision token, so it is safe for a read-only attention renderer.

`AgentTurnEvent` provides session-scoped `turn_started` and `turn_finished` (including status and optional error), but has **no permission-request variant** (`crates/ocean-agent-sdk/src/lib.rs:523-624`). The legacy `OceanEvent` does include `PermissionRequest` and `Error` (`crates/ocean-core/src/lib.rs:814-854`), and the permission policy emits that event while setting the associated request to `WaitingForPermission` (`crates/ocean-daemon/src/main.rs:2000-2054`).

### Cross-session availability verdict

**Available today, but fragmented across contracts.** A read-only Dynamic Island can poll:

1. `GET /v1/requests` for all cross-session queued/running/waiting/errored activity.
2. `GET /v1/permissions` for pending permission attention and display metadata.
3. Optionally `GET /v1/agent/sessions/{id}` to resolve title/history/error, or page `GET /v1/agent/sessions` for titles and active turns.

For live events, `GET /v1/agent/events?all=1` explicitly enables the cross-session firehose; without `session_id` and without `all=1`, session-bearing events are deliberately omitted (`crates/ocean-daemon/src/main.rs:8586-8645`). This gives live running/completion/error events but not permission prompts. Permission prompts are only on the unscoped legacy `/v1/events`, whose payload itself omits IDs; correlation IDs are envelope metadata supplied by the daemon emit path, while the event enum only contains tool/reason/args (`crates/ocean-core/src/lib.rs:835-849`, emission at `crates/ocean-daemon/src/main.rs:2030-2045`). Consuming two SSE rails is therefore possible but awkward.

Important limitation: completed/errored requests remain only until registry GC, and session list pagination means the first session page is not a guaranteed exhaustive activity index. The global request snapshot is the correct current source for attention, not session-list scanning.

### Smallest daemon contract change

No daemon change is strictly required for a polling-based Phase-2 slice: compose the two existing global GET snapshots and lazily resolve session titles.

If the Surface requires one authoritative/live attention feed, the smallest additive change is to add a generic permission-attention variant to `ocean_agent_sdk::AgentTurnEvent` containing `session_id`, `turn_id`/request correlation, `permission_id`, `tool`, `reason`, `args`, then emit it alongside the existing legacy `OceanEvent::PermissionRequest`. `GET /v1/agent/events?all=1` would then carry running, terminal errors, and permission attention on one replayable cross-session rail. Do **not** expose `decision_token`, and do not invent a separate session model. Likely change sites: `crates/ocean-agent-sdk/src/lib.rs` event enum/session-id matcher, `crates/ocean-daemon/src/event_adapter.rs` type-name/mirror handling, and the permission emission path in `crates/ocean-daemon/src/main.rs`. This is broader cross-crate shared-event work and needs SDK/daemon/client fanout checks per `crates/AGENTS.md`.

A smaller HTTP-only alternative is an additive `GET /v1/attention` projection assembled from the existing request and permission registries, but it duplicates product vocabulary in the daemon and lacks the existing SSE/replay machinery; it is less architecturally clean unless Surface explicitly wants polling and a single call.

## Architecture

`ocean-agent` persists sessions/turns; `ocean-agent-sdk` defines product-facing session/turn/event DTOs. The daemon projects persisted sessions plus its in-memory request registry into session list/detail endpoints. Runtime permission checks suspend a request, update `RequestStatus` to `WaitingForPermission`, insert a `PermissionStatus`, and emit only a legacy event. The full-fidelity agent bus is session-aware, replay-bounded, and optionally cross-session via `all=1`, but currently does not receive permission events.
